# Jev and the coach decision layer

Notes for later: what changed, why, and how to try it locally.
Branch: `jev` · Code commit: `882bd88` (this doc and `scripts/preview-week.ts` follow it)

---

## The problem this solves

Workouts were generated by asking a chat model once, at `temperature: 0.7`, to pick movements from a shortlist. Schema validation proved the result was *legal* — right slot count, known movement IDs, doses in range — but not that it was *good*. "Chip Happens" is the canonical example: five dumbbell movements, 100 reps of grip and shoulder work, all inside a 20-minute cap. Every pattern was technically distinct, so validation passed.

Three separate causes, and they needed three separate fixes:

| Cause | Symptom | Fix |
| --- | --- | --- |
| Selection was random | `hash(date) % menu`, rotate by seed, "prefer the first ID" | Week-aware class scoring + pattern rest |
| No whole-session constraints | Implement stacks, volume vs. cap, prep = workout | `lib/engine/quality.ts` |
| No taste layer | One shot, no second opinion | `lib/decide/` (Jev or an LLM) |

A decision model alone would not have fixed this. It can only reject; it cannot invent a barbell that isn't in the gym, and it cannot do the arithmetic. The engine still owns structure, doses, schemes, and feasibility. Jev owns judgment.

---

## The three-part split

```
ENGINE     — shapes the week, chooses schemes, slots, doses, time caps.
             Deterministic, free, always available.
             lib/engine/*

DECISION   — judges and selects: "does this read like a real class?",
LAYER        "is the volume honest?", "does the week need this?".
             Optional. lib/decide/*

CHAT MODEL — writes the title and the stimulus line. The only job that
             genuinely needs generation.
```

Rule of thumb: **exact answers → code; bounded judgments → decision layer; prose → LLM.**

## What changed, file by file

### New: `lib/engine/quality.ts`

A deterministic audit over a composed `ClassPlan`. No network, no cost. Runs on every generated session.

| Code | Severity | Fires when |
| --- | --- | --- |
| `implement_stack` | hard | 4+ movements share one implement (dumbbell/barbell/kettlebell) |
| `implement_run` | hard | 3+ same-implement movements back to back |
| `grip_overload` | hard | 3+ grip-taxing movements (loaded hinge/olympic/carry/pull/lunge, pull-ups) |
| `overhead_stack` | soft | 3+ overhead movements |
| `station_too_long` | hard | An EMOM/interval station needs > 95% of its window |
| `round_too_long` | hard | An AMRAP round takes > 4 min |
| `round_too_short` | soft | An AMRAP round takes < 45 s |
| `volume_over_cap` | hard | Estimated work > 105% of the time cap |
| `volume_under_cap` | soft | Estimated work < 30% of the time cap |
| `prep_repeats_work` | hard | 3+ primer sets repeat workout movements |
| `class_too_long` | soft | Warm-up + prep + work + cool-down > 75 min |

Scoring: `100 − 40×hard − 10×soft`, floored at 0. `betterPlan()` compares two plans by hard, then soft, then score.

Work estimates are heuristics on purpose (3 s per loaded rep, 2 s per bodyweight rep, 0.27 s/m, 4 s/cal). They exist to catch outliers, not to predict a score.

### Changed: `lib/ai.ts`

`composePlan()` no longer trusts one answer:

```
assignment (shape, scheme, slots)
  ├── chat model  → 1 session
  └── engine      → 4 variants (different shortlist rotations)
        ↓
  auditPlan() every candidate        (free, deterministic)
        ↓
  bestFallback = fewest hard → fewest soft → highest score
        ↓
  decider configured?
    judgeCandidates([aiPlan, bestFallback]) in parallel
    keep the model's unless it is rejected, or the engine's
    confidence is > 0.1 higher
        ↓
  savePlan() stores audit metadata in the day's `program` JSON
```

`VARIANTS = 4` is in `lib/ai.ts`. Variants cost nothing but CPU: no extra model calls.

Also: `recentSignals()` now parses `shape` from the stored `program` JSON, so week logic has real history.

### Changed: `lib/engine/planner.ts`

- `pickClass()` scores the class menu against the last 7 days instead of hashing the date alone. Recent shapes and shape families are penalised; unseen shapes are rewarded; chippers are spread out (at most one long session per week, roughly).
- `avoidPatterns` now reads patterns from the last 4 days' *movements*, not just one headline pattern per day, rather than the last 2 days.
- New `loadedAnchorPattern()` picks a loaded pattern that (a) has an eligible staple in your gym and (b) hasn't been trained this week. This is the fix for "deadlift again?".
- New `gymPatternChoice()` does the same for gymnastics slots, choosing among press / pull / jump / core / squat. Previously this slot was pinned to press, which is why push-ups appeared daily.
- `tripletSlots`, `quadSlots`, `chipperSlots`, `coupletSlots` all take a seed and the avoid list, and are guaranteed to produce distinct patterns where the gym allows it.
- `shortlistForPiece()` accumulates implements across slots so the second loaded slot prefers a different implement.
- Determinism is preserved: same date + same history = same class.

### Changed: `lib/engine/class.ts`

- `buildFallbackClass({ ..., variant })` and `buildFallbackPiece(..., variant)` can rotate the pick within each slot's candidate group. Variant 0 behaves exactly as before.
- `buildPrep()` limits primer sets to 2 workout movements and skips menu drills that duplicate a workout movement name. Prep primes; it does not pre-fatigue.

### Changed: `lib/engine/roles.ts`

- `availableGymPatterns(profile)` / `availableLoadedPatterns(profile)` report which patterns actually have an eligible staple in this gym.
- `candidatesForSlot(..., usedImplements)` penalises an implement already used earlier in the piece.

### New: `lib/decide/`

| File | Purpose |
| --- | --- |
| `types.ts` | `Noul` / `Score` / `Choice` question and answer types, `Decider` interface |
| `typesafe.ts` | Jev backend: `POST /v1/systemone`, Bearer key |
| `llm.ts` | Same contract answered by the configured chat model |
| `questions.ts` | The six session questions and the state renderer |
| `policy.ts` | When a verdict means "keep", and why not |
| `index.ts` | Backend selection, `judgeSession()`, `judgeCandidates()` |

### New: `scripts/preview-week.ts`

Engine-only week preview: prints shape, title, movements, audit score, and issue codes for seven dates, threading history through `recent` exactly as production does. No model calls, no key. See [Local testing](#local-testing).

## The decision contract

The questions are the contract, not the vendor. `lib/decide/questions.ts`:

| ID | Type | Claim a high probability supports |
| --- | --- | --- |
| `coherent` | Noul | Reads as one intentional class, not a movement pile |
| `stimulus` | Score (3) | Movements deliver the stated stimulus |
| `local_fatigue` | Noul | One implement/joint carries the work — **high is bad** |
| `volume` | Noul | Completable inside the cap at the intended effort |
| `contrast` | Noul | Movements contrast rather than repeat stress |
| `week_fit` | Noul | Adds what the week is missing |

The state is a compact rendering of the class plus the last six sessions:

```
TITLE: Row & Press
STIMULUS: Hard, but repeatable.
FOCUS: mixed

PREP:
- 5 cal Row
- 5 Dumbbell Push Press

WORK:
Workout — amrap
- 12 cal Row
- 10 reps Dumbbell Push Press
- 12 reps Box Jump

RECENT SESSIONS (most recent first):
2026-10-30: heavy (hinge, heavy)
...
```

### Jev wire format

```
POST https://api.typesafe.ai/v1/systemone
Authorization: Bearer $TYPESAFE_API_KEY
Content-Type: application/json
```

```json
{
  "state": "TITLE: Row & Press\n...",
  "model": "jev-latest",
  "questions": {
    "coherent": {
      "type": "noul",
      "instructions": "This reads as one intentional CrossFit class a coach would put on the whiteboard, not a pile of movements assembled to fill a time slot."
    },
    "stimulus": {
      "type": "score",
      "instructions": "How well the movements deliver the stimulus the class claims.",
      "criteria": ["The movements fight the stimulus", "Workable but muddled", "Textbook for this stimulus"]
    },
    "local_fatigue": {
      "type": "noul",
      "instructions": "One implement, joint, or muscle group carries so much of the work that local fatigue, not conditioning, will decide the score."
    }
  }
}
```

Response (abridged):

```json
{
  "model": "jev-1.13.0",
  "answers": {
    "coherent": { "type": "noul", "noul": 0.91 },
    "stimulus": { "type": "score", "score": 1.85, "confidence": 0.62 },
    "local_fatigue": { "type": "noul", "noul": 0.07 }
  }
}
```

### Policy (`lib/decide/policy.ts`)

A class is **kept** when all of these hold:

| Signal | Rule |
| --- | --- |
| `coherent` | `>= AI_DECIDER_THRESHOLD` (default `0.6`) |
| `local_fatigue` | `< threshold` |
| `volume` | `>= threshold` |
| `contrast` | `>= threshold` |
| `week_fit` | `>= 0.45` |
| `stimulus` | `>= 1` (on the 0–2 scale) |

Any failure produces a human-readable reason, logged when the model's session is rejected:

```
[coach] judged the model's session unfit: local fatigue will decide the score; volume does not fit the cap.
```

Probability is evidence, not truth. These thresholds are business rules and live in code so they can be reviewed.

## Configuration

| Variable | Default | Notes |
| --- | --- | --- |
| `AI_DECIDER` | `auto` | `auto`, `typesafe`, `llm`, `off` |
| `TYPESAFE_API_KEY` | — | Key from <https://console.typesafe.ai/keys> |
| `TYPESAFE_MODEL` | `jev-latest` | |
| `TYPESAFE_BASE_URL` | `https://api.typesafe.ai/v1` | Only for a proxy |
| `TYPESAFE_TIMEOUT_MS` | `20000` | Per request |
| `AI_DECIDER_THRESHOLD` | `0.6` | Clamped to 0.05–0.95 |

`auto` means: use TypeSafe if a key exists, otherwise off. **No key, no change in behaviour.** A decider failure (timeout, 500, malformed answer) is caught and logged; the deterministic result stands.

Keys are read server-side only (`lib/env.ts`); nothing reaches the browser.

### 3. LLM decider (no TypeSafe key)

```bash
AI_DECIDER=llm npm run dev
```

Generate a day. The same six questions go to your configured chat model, parsed and clamped by `lib/decide/llm.ts`. Watch the server log for `[coach] judged the model's session unfit: ...`. This is the cheapest way to see whether the criteria agree with your taste before adding a vendor.

Note: an ordinary chat model's probabilities are not calibrated. The verdict still works, but the margins mean less.

### 4. Jev

```bash
TYPESAFE_API_KEY=ts-... npm run dev
```

`AI_DECIDER=auto` picks it up. Two requests per generation, in parallel, ~100–500 ms each. If you want to force it:

```bash
AI_DECIDER=typesafe TYPESAFE_API_KEY=ts-... TYPESAFE_MODEL=jev-latest npm run dev
```

Sanity checks:

- Server log should stay quiet. A `[decide] typesafe could not judge...` line means the key, URL, or response shape is wrong.
- A `[coach] judged...` line means the judge is working and disagreed with the chat model.
- Compare `quality.score` in the database (below) before and after.

### 5. Inspect what was saved

Every generated day stores the audit in `workout_days.program`:

```bash
sqlite3 data/tg.sqlite <<'SQL'
select date,
       json_extract(program, '$.shape')            as shape,
       json_extract(program, '$.quality.score')    as score,
       json_extract(program, '$.quality.hard')     as hard,
       json_extract(program, '$.quality.codes')    as codes
from workout_days
where json_valid(program)
order by date desc
limit 10;
SQL
```

`codes` is a JSON array of the issue codes that survived. Empty means the audit found nothing.

To compare candidate quality over time, regenerate a set of dates and check that `hard` is always 0 and `score` trends to 100. A nonzero hard code is a bug or a genuinely constrained day (limited gear), not a taste disagreement.

## Tuning

Three places, in order of how often you'll touch them:

1. **`lib/decide/questions.ts`** — the taste. Reword a claim, add a question, or split "coherent" into "sequencing" and "stimulus fit". Every question is a claim you can disagree with in writing, which is the point.
2. **`lib/decide/policy.ts`** — the rules. Which signals can veto, and at what probability. `AI_DECIDER_THRESHOLD` raises or lowers all Noul thresholds at once.
3. **`lib/engine/quality.ts`** — the hard constraints and the seconds-per-rep heuristics. Raise the grip limit if your athletes have hands of iron; lower it if forearms always fail first.

### How to know if it's working

Label ~30 generated sessions yourself as good/bad (you're the coach, and the sessions are already in the database). Then compare your labels to the `keep` verdicts and to `quality.score`.

- If Jev rejects classes you like, its criteria are too strict or the question is badly worded.
- If it keeps classes you don't like, a constraint is missing from `quality.ts` — the judge is only as good as the claims.
- If both agree but the workouts are still flat, the problem is the candidate set, not the judge: add variants or widen the shortlists.

There is no calibration harness yet. That's the honest next step.

## Known limits

- **The judge only compares two candidates**: the chat model's session and the engine's best of four. It does not rank all five. Full best-of-five with Jev is a small change in `composePlan`.
- **Verdicts are not persisted.** Only the deterministic audit lands in the database. Judge output goes to the server log. Storing it would make tuning much easier.
- **The `Choice` primitive is unused.** The obvious next use is slot-level repair: "given this piece and these five candidates, pick the replacement that fixes grip overload."
- **Work estimates are heuristics.** They will disagree with a real athlete's pace; tune the constants rather than trusting the score as a measurement.
- **Jev is early access.** The wire format can change. It is isolated in `lib/decide/typesafe.ts` and `typesafeConfigured()` for exactly this reason.
- **The engine does more work per generation** (four variants + audit). It is CPU-only and measured in milliseconds, but it is not free.
- **The chat model still writes title and stimulus**, and a swapped-in engine variant gets a templated title. Titles may be less charming than before when the judge overrules the model.

## Suggested next steps

1. Persist the verdict (`keep`, confidence, reasons) next to `quality` in the day's `program` JSON.
2. Add a `scripts/label-quality.ts` that dumps recent sessions and lets you mark good/bad, then prints agreement.
3. Use Jev's `Choice` for slot repair instead of regenerating a whole session.
4. Move week-level class selection into a Jev `Choice` over the nine menu entries, with the current scoring function as the deterministic backend.
5. Consider a second judge pass on the *week*, not just the day.

## Rollback

The change lives on its own branch:

```bash
git checkout main          # leave the branch
git log --oneline jev      # see the commits
git revert <sha>           # or revert in place
```

No schema migration, no data rewrite. The only stored change is an extra `quality` key in the `program` JSON, which older code ignores.

---

## TL;DR

- The engine still programs. The decision layer only judges and selects.
- Without a key, generation is unchanged except that it is now audited, ranked, and week-aware.
- With `TYPESAFE_API_KEY`, Jev gets a second opinion on the model's session for a fraction of a cent.
- The questions are the interesting artifact. Prompts drift; criteria can be reviewed.
